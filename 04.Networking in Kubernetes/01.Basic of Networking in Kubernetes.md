# Basic of Networking in Kubernetes

## 단일 노드 네트워킹

- 노드에는 **IP 주소**가 있다. 쿠버네티스 노드에 접속할 때 사용하는 바로 그 주소다.
- minikube를 쓴다면 로컬 머신(하이퍼바이저/Docker) 안에 있는 **minikube 가상 머신(노드)의 IP**를 말한다.
- 단일 노드 클러스터에 Pod를 하나 만들면, Pod는 컨테이너를 호스트하고 **Pod에 IP 주소가 할당**된다.

### Pod IP는 어디서 올까?

- 쿠버네티스는 클러스터를 구성할 때 **내부 사설 네트워크**를 만든다. 예: `10.244.0.0/16`
- 모든 Pod가 이 네트워크에 연결되고, Pod를 여러 개 배포하면 각각 이 대역에서 **별도의 IP**를 받는다.
- Pod끼리는 이 IP로 서로 통신할 수 있다.

> **주의**: Pod IP는 Pod가 다시 만들어질 때 **바뀔 수 있다.** 그래서 Pod IP로 다른 Pod에 직접 접근하는 것은 좋은 방법이 아니다. (안정적인 접근 방법은 이후 **Service**에서 다룬다.)

## 멀티 노드에서 생기는 문제

단일 노드의 네트워킹은 이해하기 쉽다. 노드가 여러 개라면 어떻게 될까?

노드 두 개로 클러스터를 구성한다고 가정한다.

| 노드 | 노드 IP | Pod | Pod IP |
|------|---------|-----|--------|
| Node 1 | `192.168.1.2` | 1개 | `10.244.0.2` |
| Node 2 | `192.168.1.3` | 1개 | `10.244.0.2` |

- 노드 IP(`192.168.1.x`)는 서로 다르지만, 각 노드 안의 **내부 Pod 네트워크 주소는 동일**하다.
- 두 노드가 같은 클러스터에 속하면 **Pod IP가 충돌**해서 제대로 동작하지 않는다.

### 쿠버네티스는 네트워킹을 자동 구성하지 않는다

- 쿠버네티스는 클러스터를 설정할 때 이 문제를 해결해 주는 네트워킹을 **자동으로 구성하지 않는다.**
- 대신 아래 **네트워킹 요구사항**을 충족하는 네트워킹 솔루션을 사용자가 **직접 설정하기를 기대**한다.

| 요구사항 | 설명 |
|----------|------|
| Pod ↔ Pod | 클러스터의 모든 Pod는 **NAT 없이** 서로 통신할 수 있어야 한다. |
| 노드 → Pod | 모든 노드는 모든 Pod와 통신할 수 있어야 한다. |
| Pod → 노드 | 모든 Pod는 클러스터의 모든 노드와 통신할 수 있어야 한다. |

## 네트워킹 솔루션 (CNI 플러그인)

직접 구현할 필요 없이, 요구사항을 충족하는 **미리 만들어진 솔루션**을 쓰면 된다.

- Flannel
- Calico
- Cilium
- Weave Net
- Cisco ACI
- Big Cloud Fabric
- VMware NSX-T 등

배포 플랫폼에 따라 적합한 솔루션을 선택한다. 자체 시스템에 처음부터 클러스터를 구축한다면 이 중 하나를 직접 골라 설치한다.

> 이 솔루션들은 **CNI(Container Network Interface)** 표준을 따르는 플러그인으로 설치된다. kubelet이 Pod를 만들 때 CNI 플러그인을 호출해 Pod에 IP를 부여하고 네트워크에 연결한다.

## Flannel / Calico를 쓰는 클러스터

네트워킹을 Flannel이나 Calico로 설정한 클러스터에서는 다음과 같이 동작한다.

1. 네트워킹 솔루션이 노드의 네트워크와 IP 주소를 **관리**한다.
2. **노드마다 서로 다른 Pod 네트워크 대역**을 할당한다.
3. 모든 Pod와 노드를 아우르는 **가상 네트워크**가 만들어지고, 모든 Pod가 **고유한 IP**를 받는다.
4. 간단한 **라우팅 기술**로 노드 간 Pod 통신이 이루어져 쿠버네티스 네트워킹 요구사항을 충족한다.
5. 결과적으로 모든 Pod는 **할당된 IP로 서로 통신**할 수 있다.

| 노드 | 노드 IP | Pod 대역 | Pod IP 예시 |
|------|---------|----------|-------------|
| Node 1 | `192.168.1.2` | `10.244.1.0/24` | `10.244.1.2` |
| Node 2 | `192.168.1.3` | `10.244.2.0/24` | `10.244.2.2` |
| Node 3 | `192.168.1.4` | `10.244.3.0/24` | `10.244.3.2` |

- 전체 Pod 네트워크(`10.244.0.0/16`)를 노드 수만큼 잘게 나눠 **노드별로 하나씩 배정**하므로 IP가 겹치지 않는다.
- 노드 간 전달 방식은 솔루션마다 다르다. Flannel은 주로 **VXLAN 오버레이**(패킷을 캡슐화해 전달), Calico는 **BGP 라우팅**(오버레이 없이 라우팅 경로를 교환)을 쓴다.

## 보강: 클러스터 네트워킹 정리

### 네트워크 대역 구분

쿠버네티스에는 서로 다른 세 종류의 IP 대역이 있다.

| 종류 | 예시 | 설명 |
|------|------|------|
| 노드 네트워크 | `192.168.1.0/24` | 노드(VM/서버)가 속한 실제 네트워크 |
| Pod 네트워크 | `10.244.0.0/16` | CNI 플러그인이 관리하는 Pod IP 대역 |
| Service 네트워크 | `10.96.0.0/12` | Service의 가상 IP(ClusterIP) 대역. kube-apiserver의 `--service-cluster-ip-range`로 지정 |

> 세 대역은 **서로 겹치지 않아야** 한다.

### 확인해 보기

```bash
# 노드 IP 확인
kubectl get nodes -o wide

# Pod IP와 배치된 노드 확인
kubectl get pods -o wide

# minikube 노드 IP
minikube ip
```

`kubectl get pods -o wide` 결과의 `IP` 열이 Pod IP, `NODE` 열이 Pod가 배치된 노드다.

### 알아 두면 좋은 점

- **Pod 안의 컨테이너**는 같은 네트워크 네임스페이스를 공유하므로 `localhost`로 서로 통신한다.
- **Pod IP는 일시적**이다. Pod가 재생성되면 IP가 바뀌므로, 고정된 접근 지점이 필요하면 **Service**를 사용한다.
- **CNI 플러그인이 설치되지 않으면** 노드가 `NotReady` 상태가 되고 Pod가 `ContainerCreating`에서 멈출 수 있다.
- **NetworkPolicy**(Pod 간 트래픽 제한)는 CNI가 지원해야 동작한다. Calico·Cilium은 지원하지만 Flannel은 지원하지 않는다.
- minikube는 기본적으로 단일 노드라 이 문제를 겪지 않지만, 멀티 노드(`minikube start --nodes 2`)나 `--cni=calico` 같은 옵션으로 실험해 볼 수 있다.
