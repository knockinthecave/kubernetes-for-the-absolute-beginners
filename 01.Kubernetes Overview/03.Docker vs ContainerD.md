# Docker vs containerd

## 배경

- 컨테이너 초창기에는 Docker, rkt(Rocket) 등이 있었다.
- Docker는 컨테이너 작업을 매우 간단하게 만든 사용자 경험 덕분에 가장 지배적인 컨테이너 도구가 되었다.
- 이런 컨테이너를 **오케스트레이션**하기 위해 쿠버네티스가 등장했고, 초기 쿠버네티스는 **Docker로만** 실행할 수 있었다.

## CRI와 OCI

### CRI (Container Runtime Interface)

rkt 같은 다른 컨테이너 런타임도 쿠버네티스와 함께 동작할 수 있도록 도입된 **인터페이스**.
CRI를 구현한 런타임이면 쿠버네티스에서 사용할 수 있다.

### OCI (Open Container Initiative)

모든 벤더가 OCI 표준을 준수하는 한 컨테이너 런타임으로 동작할 수 있도록 하는 표준. 두 가지 사양으로 구성된다.

| 사양 | 정의하는 내용 |
|------|---------------|
| 이미지 사양 (image-spec) | 이미지를 빌드하는 방법 |
| 런타임 사양 (runtime-spec) | 컨테이너 런타임을 개발하는 방법 |

## Docker와 dockershim

- Docker는 CRI가 도입되기 **이전**부터 쓰이고 있었기 때문에, CRI를 따르지 않는다.
- 그럼에도 Docker를 계속 지원해야 했으므로, 쿠버네티스는 **dockershim**이라는 임시 계층을 두어 CRI 없이 Docker를 연결했다.
- dockershim을 유지하는 것은 수고와 복잡성을 더했고, 결국 **완전히 제거**되어 쿠버네티스의 Docker 직접 지원이 끝났다(v1.24).
- Docker로 빌드한 이미지는 모두 OCI 이미지 사양을 따르므로 **계속 사용할 수 있다.**

## containerd

- 컨테이너 런타임인 **runc**를 관리하는 데몬. 원래 Docker의 일부였으나 지금은 독립된 프로젝트(CNCF graduated)다.
- CRI를 지원하므로 다른 런타임과 마찬가지로 쿠버네티스와 직접 연동된다.
- Docker 없이 단독으로 설치해 런타임으로 쓸 수 있으며, **Docker 설치 없이 containerd만 설치하는 것이 이상적**이다.

## Docker vs containerd 비교

| 구분 | Docker | containerd |
|------|--------|------------|
| 성격 | 컨테이너 플랫폼 (빌드·배포·실행 도구 모음) | 컨테이너 런타임 (실행·이미지 관리에 집중) |
| 구성 | Docker CLI, Docker API, 이미지 빌드, 볼륨, 보안 등 + 내부적으로 containerd 사용 | runc를 관리하는 데몬 |
| CRI 지원 | 없음 (dockershim 필요했음) | 있음 (직접 연동) |
| 쿠버네티스 지원 | v1.24부터 직접 지원 제거 | 기본 지원 런타임 |
| 이미지 빌드 | `docker build` 지원 | 자체 빌드 기능 없음 (BuildKit 등 별도 도구) |
| 규모 | 무겁고 기능이 많음 | 가볍고 단순 |
| 독립 사용 | Docker 전체 설치 필요 | 단독 설치 가능 |

## containerd용 CLI

containerd를 쓰는 환경에서는 `docker` 명령어 대신 다음 도구를 사용한다.

| 도구 | 설명 | 용도 |
|------|------|------|
| `ctr` | containerd에 포함된 기본 CLI | 디버깅용. 사용자 친화적이지 않고 기능이 제한적 |
| `nerdctl` | Docker CLI와 호환되는 containerd용 CLI | 일반적인 컨테이너 작업 (`docker`와 거의 같은 사용법) |
| `crictl` | CRI 호환 런타임용 CLI (쿠버네티스 커뮤니티 제공) | 쿠버네티스 노드의 컨테이너 디버깅·점검 |

```bash
# docker 명령어와 비교
docker run -d nginx        # Docker
nerdctl run -d nginx       # containerd (nerdctl)
crictl ps                  # 쿠버네티스 노드의 컨테이너 조회
ctr images ls              # containerd 이미지 목록 (디버깅용)
```

## 쿠버네티스는 어떻게 Docker 지원을 중단할 수 있었나

세 가지 조건이 맞물렸기 때문이다.

1. **CRI가 런타임을 추상화했다.**
   kubelet은 특정 런타임이 아니라 CRI라는 표준 인터페이스와만 통신한다. CRI를 구현한 런타임이면 무엇이든 교체할 수 있으므로 Docker가 반드시 필요한 존재가 아니게 되었다.
2. **Docker 안에 이미 containerd가 있었다.**
   실제 컨테이너 실행은 Docker가 아니라 그 안의 containerd(→ runc)가 맡는다. 쿠버네티스가 필요한 것은 이 부분뿐이므로 containerd를 직접 쓰면 Docker 계층은 군더더기가 된다.

   ```
   (이전)  kubelet → dockershim → dockerd → containerd → runc
   (이후)  kubelet → (CRI) → containerd → runc
   ```
3. **OCI 표준이 이미지 호환성을 보장했다.**
   Docker로 빌드한 이미지는 OCI 이미지 사양을 따르므로 containerd 같은 다른 런타임에서도 그대로 실행된다. 런타임을 바꿔도 사용자의 이미지는 영향을 받지 않는다.

결국 dockershim은 CRI를 따르지 않는 Docker를 억지로 연결하던 **쿠버네티스 내부의 임시 어댑터**였고, 유지 비용(수고와 복잡성)만 남았기 때문에 제거되었다(v1.24).

### 제거로 영향받는 경우

- **영향 없음**: Docker로 빌드한 이미지를 쿠버네티스에서 실행하는 일반적인 사용.
- **영향 있음**: 노드의 Docker 소켓(`/var/run/docker.sock`)에 직접 의존하는 워크로드(Docker-in-Docker, 노드에서 `docker` 명령 사용 등). containerd 기반 도구(`crictl`, `nerdctl`)로 바꿔야 한다.
- 그래도 Docker를 런타임으로 계속 쓰고 싶다면 외부 어댑터인 **cri-dockerd**를 별도로 설치하는 방법이 있다.

## 정리

- Docker의 이미지는 OCI 표준이라 어떤 런타임에서도 동작한다.
- 쿠버네티스는 CRI를 구현한 런타임(containerd, CRI-O 등)을 사용한다.
- 쿠버네티스 노드에는 Docker 없이 containerd만 설치하는 구성이 가장 가볍고 이상적이다.
