# Services & NodePort

## Service란?

- Service는 애플리케이션 **내부와 외부의 다양한 구성 요소 간 통신**을 가능하게 한다.
- **Pod 그룹 간의 연결**을 담당하며, 애플리케이션을 다른 애플리케이션이나 사용자와 연결해 준다.
  - 최종 사용자가 프론트엔드 애플리케이션에 접근할 수 있게 한다.
  - 프론트엔드 ↔ 백엔드 Pod 간 통신을 돕는다.
  - 외부 데이터 소스와의 연결을 설정한다.
- 덕분에 마이크로서비스 간 **느슨한 결합(loose coupling)** 이 가능하다.

## 왜 필요한가? (사용 사례)

웹 애플리케이션이 실행되는 Pod를 배포했다고 하자. 외부 사용자는 이 웹 페이지에 어떻게 접근할까?

| 대상 | IP 예시 | 네트워크 |
|------|---------|----------|
| 쿠버네티스 노드 | `192.168.1.2` | 노드 네트워크 |
| 내 노트북 | `192.168.1.10` | 노드와 같은 네트워크 |
| Pod | `10.244.0.2` | 내부 Pod 네트워크 (`10.244.x.x`) |

- 노트북은 노드와 같은 네트워크(`192.168.1.x`)에 있지만, Pod는 **별도의 내부 네트워크**(`10.244.x.x`)에 있다.
- 따라서 노트북에서 `10.244.0.2`로 **ping하거나 접근할 수 없다.**

### 노드 안에서라면 접근 가능

1. 노드(`192.168.1.2`)에 **SSH로 접속**해서 `curl http://10.244.0.2`로 웹 페이지를 확인한다.
2. 노드에 GUI 브라우저가 있다면 노드에서 `http://10.244.0.2`를 열어 확인한다.

하지만 이것은 **노드 내부에서만 되는 방법**이라 사용자가 원하는 형태가 아니다.

### 원하는 것

- 노드에 SSH로 접속하지 않고, **노트북에서 노드 IP(`192.168.1.2`)로 접속**하는 것만으로 웹 서버에 닿아야 한다.
- 즉 **노트북 → 노드 → Pod(웹 컨테이너)** 로 요청을 매핑해 주는 장치가 필요하다. 이것이 **Service**다.

## Service 유형

Service는 Pod, ReplicaSet, Deployment처럼 쿠버네티스 **오브젝트**다.
대표적인 사용 사례는 **노드의 포트를 수신(listen)하다가 그 요청을 Pod의 포트로 전달**하는 것이다.

| 유형 | 설명 |
|------|------|
| **NodePort** | 노드의 포트를 열어, 그 포트로 들어온 요청을 내부 Pod로 전달한다. 외부에서 Pod에 접근 가능. |
| **ClusterIP** | 클러스터 내부에 **가상 IP**를 만들어 서비스 간(예: 프론트엔드 ↔ 백엔드) 통신을 가능하게 한다. |
| **LoadBalancer** | 지원되는 **클라우드 제공업체**의 로드 밸런서를 프로비저닝한다. 예: 프론트엔드 계층의 여러 웹 서버로 부하 분산. |

> `type`을 생략하면 기본값은 **ClusterIP**다.

## NodePort

### 세 가지 포트

노드 → Service → Pod 순으로 요청이 전달되며, 각 구간마다 포트가 있다.

```
노트북 ──▶ 노드 IP:30008 ──▶ Service(ClusterIP):80 ──▶ Pod IP:80
           (nodePort)         (port)                    (targetPort)
```

| 포트 | 위치 | 설명 | 예시 |
|------|------|------|------|
| `targetPort` | **Pod** | 실제 웹 서버가 listen하는 포트. Service가 요청을 **전달하는 대상** 포트 | `80` |
| `port` | **Service** | Service 자체의 포트 | `80` |
| `nodePort` | **노드** | 외부에서 접근할 때 사용하는 노드의 포트 | `30008` |

- 이 이름들은 **Service 관점**에서 붙여진 것이다.
- Service는 사실상 **노드 안의 가상 서버**와 같다. 클러스터 내부에 자체 IP가 있고, 이를 **Service의 ClusterIP**라고 한다.
- `nodePort`는 기본적으로 **30000 ~ 32767** 범위만 쓸 수 있다.

### 정의 파일

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  type: NodePort
  ports:
    - targetPort: 80
      port: 80
      nodePort: 30008
  selector:
    app: myapp
    type: front-end
```

### 필드 규칙

- **`port`만 필수**다.
- `targetPort`를 생략하면 `port`와 **같은 값**으로 간주한다.
- `nodePort`를 생략하면 유효 범위(30000~32767)에서 **빈 포트가 자동 할당**된다.
- `ports`는 **배열**이므로(`-`로 시작) 하나의 Service에 **여러 포트 매핑**을 둘 수 있다.

### Service와 Pod 연결: label & selector

- 위 정의 파일에는 **어느 Pod로 보낼지**에 대한 내용이 `ports` 안에 없다. `targetPort: 80`이 어느 Pod의 80번인지 알 수 없다.
- ReplicaSet에서 했던 것과 같이, 쿠버네티스에서 자주 쓰는 기법인 **label과 selector**로 연결한다.

1. 대상 Pod는 정의 파일에서 `labels`를 가지고 있다.
2. 그 label을 Service 정의 파일의 `spec.selector` 아래에 그대로 가져온다.
3. 이렇게 하면 Service가 해당 label을 가진 Pod에 연결된다.

```yaml
# pod-definition.yml
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:          # ─┐ 이 label을
    app: myapp     #  │
    type: front-end # ─┘
spec:
  containers:
    - name: nginx-container
      image: nginx
```

```yaml
# service-definition.yml
spec:
  selector:        # ─┐ selector에 그대로 가져온다
    app: myapp     #  │
    type: front-end # ─┘
```

### 생성 및 확인

```bash
kubectl create -f service-definition.yml
kubectl get services
```

## 여러 Pod / 여러 노드의 경우

### 한 노드에 여러 Pod

- 프로덕션에서는 **고가용성과 로드 밸런싱**을 위해 같은 웹 애플리케이션 Pod를 여러 개 실행한다.
- 이 Pod들은 모두 **같은 label**(`app: myapp`)을 가진다.
- Service를 만들면 selector와 일치하는 Pod를 모두 찾고(예: 3개), **자동으로 전부 엔드포인트로 등록**해 외부 요청을 전달한다.
- 별도 설정은 필요 없다. 분산 방식은 **무작위(random) 알고리즘**이며, Service가 **내장 로드 밸런서** 역할을 한다.

> 연결된 엔드포인트는 `kubectl get endpoints myapp-service`로 확인할 수 있다.

### 여러 노드에 Pod 분산

- Pod가 클러스터의 **여러 노드에 흩어져** 있어도 추가 설정이 필요 없다.
- Service를 만들면 쿠버네티스가 **클러스터의 모든 노드에 걸쳐** Service를 만들고, `targetPort`를 **모든 노드의 동일한 `nodePort`** 에 매핑한다.

| 노드 | 접근 주소 |
|------|-----------|
| Node 1 | `curl http://192.168.1.2:30008` |
| Node 2 | `curl http://192.168.1.3:30008` |
| Node 3 | `curl http://192.168.1.4:30008` |

- **어느 노드 IP로 접근해도** 같은 포트(`30008`)로 같은 웹 애플리케이션에 닿는다.

## 정리

- 단일 노드·단일 Pod, 단일 노드·여러 Pod, 여러 노드·여러 Pod 어느 경우든 **Service 생성 방식은 완전히 동일**하다.
- Pod가 추가되거나 제거되면 Service가 **자동으로 업데이트**되므로 매우 유연하다.
- 한 번 만들어 두면 보통 **추가로 설정을 바꿀 일이 없다.**

## 보강: 알아 두면 좋은 점

- **`selector`는 label 일치 여부만 본다.** Pod 이름이나 Deployment와는 무관하다. label이 틀리면 Service는 만들어져도 엔드포인트가 비어 있어 접속되지 않는다.
- **minikube(Docker 드라이버, macOS)** 에서는 노드 IP로 직접 접속이 안 될 수 있다. 이때는 아래 명령으로 접근한다.

  ```bash
  # 터널을 열고 접근 URL 출력 (터미널을 켜 둬야 함)
  minikube service myapp-service --url
  ```

- `kube-proxy`가 각 노드에서 Service로 온 트래픽을 Pod로 전달하는 규칙(iptables 등)을 관리한다. 위의 "무작위 분산"도 이 규칙으로 구현된다.
