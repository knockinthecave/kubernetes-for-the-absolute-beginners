- 가정
어플리케이션이 이미 개발이 완료되어 빌드 후 도커 리포지토리에 있어서 쿠버네티스가 끌어서 사용가능한 상황
클러스터가 이미 설정되어 가동중
단일 노드 혹은 다중 노드 설정

모든 서비스는 앞서 쿠버네티스에서 설명한대로 실행중인 상태여야함.

- Pod
궁극적인 목표는 클러스터 워커 노드로 구성된 머신 세트에 컨테이너 형태로 어플리케이션을 배포
쿠버네티스는 워커 노드에 컨테이너를 직접 배포하지않음
Pod라는 쿠버네티스 오브젝트로 캡슐화함.
파드는 어플리케이션의 단일 인스턴스
쿠버네티스에서 생성할 수 있는 가장 작은 오브젝트

엑세스 사용자 수가 많아지면 웹 어플리케이션의 인스턴수 수를 증가시켜야함.
동일한 파드에 불러오는게 아니라 새 인스턴스와 함께 파드를 생성함
사용자 수가 더 증가해서 노드에 충분한 용량이 없으면 클러스터의 새 노드에 추가 파드를 배포하게됨.
불리적 용량을 확장하기 위해 새 노드를 추가함.

일반적으로 어플리케이션을 실행하는 컨테이너와 파드가 1:1관계를 가짐.
스케일업은 새 파드를 생성하고 스케일 다운은 기존 파드를 다운함.
어플리케이션 확장을 위해 기존 파드에 컨테이너를 추가하지 않음.

이게 이해해야할 기본적인 개념.

포드는 일반적으로 컨테이너와 1:1임.
하나의 포드에 여러개의 컨테이너가 있을 수 있지만, 일반적으로 같은 종류의 컨테이너가 여러개가 아니라는 점임
여러개의 컨테이너가 있을 수 있음.

헬퍼 컨테이너를 어플리케이션 컨테이너화 함께 배치할 시나리오라고 가정하면,
새 어플리케이션 컨테이너가 생성될때 이 두 컨테이너를 동일한 파드에 포함시킬 수 있음.

두 컨테이너는 동일한 파드의 일부이므로 동일한 네트워크 공간을 공유하기 때문에 로컬호스트 통신이 가능함.
동일한 저장 공간을 공유할 수도 있음.

파드가 어떤 컨테이너로 구성되는지 정의하기만 하면 기본적으로 파드의 컨테이너는 동일한 스토리지, 네트워크 네임스페이스에 접근할 수 있고
동일한 운명(생성 및 소멸)을 가짐.

kubectl run nginx --image nginx
-> 파드를 생성하여 도커 컨테이너를 배포함.
따라서 먼저 자동으로 파드를 생성하고 nginx 도커 이미지의 인스턴스를 배포함.

어플리케이션 이미지는 어디서 오냐?
매개변수를 사용해서 이미지 이름을 명시함.

kubectl get pods 클러스터의 파드 목록을 확인하는데에 도움이 됨.
파드가 컨테이너 생성 상태에 있다가 실제로 실행되면 곧 실행상태로 바뀜.
