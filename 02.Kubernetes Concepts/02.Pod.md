# Pod

## 전제 조건

- 애플리케이션 개발이 끝나 빌드된 이미지가 Docker 리포지토리에 있어, 쿠버네티스가 끌어와(pull) 쓸 수 있는 상태.
- 클러스터가 이미 설정되어 가동 중 (단일 노드 또는 다중 노드).
- 모든 서비스가 앞서 설명한 대로 실행 중이어야 한다.

## Pod란

궁극적인 목표는 클러스터의 워커 노드에 **컨테이너 형태로 애플리케이션을 배포**하는 것이다. 다만 쿠버네티스는 컨테이너를 워커 노드에 직접 배포하지 않고, **Pod**라는 오브젝트로 캡슐화한다.

- Pod는 애플리케이션의 **단일 인스턴스**다.
- 쿠버네티스에서 만들 수 있는 **가장 작은 오브젝트**다.

## 스케일링

접속하는 사용자가 늘면 애플리케이션 인스턴스 수를 늘려야 한다.

- 기존 Pod에 컨테이너를 추가하지 않고, **새 Pod를 생성**한다.
- 노드의 용량이 부족하면 클러스터의 **새 노드에 추가 Pod를 배포**한다.
- 물리적 용량이 부족하면 **새 노드를 추가**한다.

| 동작 | 방법 |
|------|------|
| 스케일 업 | 새 Pod 생성 |
| 스케일 다운 | 기존 Pod 삭제 |

> 애플리케이션을 확장할 때 기존 Pod에 컨테이너를 추가하지 않는다. 이것이 이해해야 할 기본 개념이다.

## Pod와 컨테이너의 관계

### 기본: 1 Pod = 1 메인 컨테이너

Pod와 애플리케이션 컨테이너는 일반적으로 1:1이다.

### 멀티 컨테이너 Pod

하나의 Pod에 컨테이너가 여러 개 있을 수도 있다. 단, 같은 종류의 컨테이너를 여러 개 넣는 것이 아니라 **역할이 다른 보조 컨테이너**를 함께 두는 경우다.

- 예: 애플리케이션 컨테이너와 **헬퍼 컨테이너**를 함께 배치한다. 새 애플리케이션 컨테이너가 생성될 때 두 컨테이너가 같은 Pod에 포함된다.
- 멀티 컨테이너는 기본 패턴이 아니라, **생명주기를 같이해야 하는 보조 프로세스**가 있을 때만 쓰는 패턴이다.
- **판단 기준:** "항상 같은 노드에서 같이 뜨고 같이 죽어야 하는가?"

### 같은 Pod 안의 컨테이너가 공유하는 것

| 공유 대상 | 설명 |
|-----------|------|
| 네트워크 | 같은 네트워크 네임스페이스를 쓰므로 `localhost`로 통신할 수 있다. |
| 스토리지 | 같은 저장 공간을 공유할 수 있다. |
| 생명주기 | 함께 생성되고 함께 소멸한다(같은 운명). |

Pod가 어떤 컨테이너로 구성되는지만 정의하면, 컨테이너들은 기본적으로 같은 스토리지와 네트워크 네임스페이스에 접근한다.

## kubectl로 Pod 다루기

```bash
kubectl run nginx --image nginx   # Pod를 만들어 nginx 이미지를 실행
kubectl get pods                  # 클러스터의 Pod 목록 확인
```

- `kubectl run`은 Pod를 먼저 자동으로 생성하고, 그 안에 nginx 도커 이미지의 인스턴스를 배포한다.
- 애플리케이션 이미지는 `--image` 매개변수로 **이미지 이름을 명시**해서 지정한다. 기본적으로 Docker Hub 같은 이미지 리포지토리에서 가져온다.
- Pod는 `ContainerCreating` 상태에 있다가 실제로 실행되면 곧 `Running`으로 바뀐다.

## 실습 (minikube)

클러스터가 꺼져 있으면 `localhost:8080 connection refused` 에러가 나므로 먼저 `minikube start`로 띄운다.

```bash
kubectl run nginx --image=nginx   # pod/nginx created
kubectl get pods                  # 처음엔 ContainerCreating (0/1)
kubectl get pods                  # 이미지 pull 후 Running (1/1)
kubectl describe pod nginx        # Pod 상세 정보 + Events 확인
kubectl get pods -o wide          # IP, 배치된 노드까지 확인
```

```
NAME    READY   STATUS    RESTARTS   AGE     IP           NODE       NOMINATED NODE   READINESS GATES
nginx   1/1     Running   0          2m55s   10.244.0.3   minikube   <none>           <none>
```

### 명령어로 알 수 있는 정보

**`kubectl get pods`**

| 컬럼 | 의미 |
|------|------|
| NAME | Pod 이름 |
| READY | 준비된 컨테이너 수 / 전체 컨테이너 수 (`0/1` → `1/1`) |
| STATUS | 현재 상태 (`ContainerCreating`, `Running` 등) |
| RESTARTS | 컨테이너 재시작 횟수 |
| AGE | Pod가 생성된 후 경과 시간 |

**`kubectl get pods -o wide`** — 위 컬럼에 추가로 다음을 보여준다.

| 컬럼 | 의미 |
|------|------|
| IP | Pod의 클러스터 내부 IP |
| NODE | Pod가 배치된 노드 |

**`kubectl describe pod nginx`**

| 항목 | 의미 |
|------|------|
| Node | 배치된 노드와 노드 IP (`minikube/192.168.49.2`) |
| Labels | `kubectl run`이 자동으로 붙인 라벨 (`run=nginx`) |
| Containers | 이미지, 컨테이너 ID, 상태(`State`), 시작 시각, 재시작 횟수 |
| Conditions | Pod 준비 단계별 상태 (`PodScheduled`, `Initialized`, `Ready` 등) |
| Events | 스케줄링부터 컨테이너 시작까지의 처리 이력. 문제 원인을 찾을 때 가장 먼저 본다. |

- `kubectl describe`는 리소스 타입을 먼저 써야 한다. `kubectl describe nginx`는 `the server doesn't have a resource type "nginx"` 에러가 나고, `kubectl describe pod nginx`가 맞다.
- `describe`의 `Events`로 생명주기를 볼 수 있다: `Scheduled`(노드 배정) → `Pulling`(이미지 다운로드) → `Pulled` → `Created` → `Started`.
- Pod는 `minikube` 노드에 배치되었고, 클러스터 내부 IP(`10.244.0.3`)를 받았다. 이 IP는 클러스터 내부 전용이라 외부에서 바로 접근할 수 없다.
