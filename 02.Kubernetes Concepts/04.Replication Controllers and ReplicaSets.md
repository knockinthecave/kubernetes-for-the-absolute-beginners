# Replication Controllers and ReplicaSets

## 컨트롤러

컨트롤러는 **쿠버네티스의 두뇌**다. 쿠버네티스 오브젝트를 모니터링하다가 상태가 달라지면 그에 맞게 응답하는 프로세스다.

## 복제(Replication)가 필요한 이유

### 1. 고가용성

Pod 하나로 애플리케이션을 실행 중인데 애플리케이션이 충돌해서 Pod가 실패하면, 사용자는 더 이상 접근할 수 없다. 이를 막으려고 **둘 이상의 Pod 인스턴스**를 실행해 둔다. 한쪽이 실패해도 다른 쪽이 계속 서비스한다.

- Replication Controller는 클러스터에서 **같은 Pod의 여러 인스턴스를 실행**하게 해 고가용성을 제공한다.
- **Pod가 하나뿐이어도 쓸 수 있다.** 기존 Pod가 실패하면 자동으로 새 Pod를 만들어 준다.
- 지정한 개수(1개든 100개든)의 Pod가 항상 실행되도록 보장한다.

### 2. 부하 분산과 확장

- 사용자가 늘면 Pod를 추가로 배포해 **여러 Pod가 부하를 나눠 처리**한다.
- 노드의 자원이 부족해지면 **다른 노드에 Pod를 추가 배포**할 수 있다.
- Replication Controller는 **클러스터의 여러 노드에 걸쳐** 동작한다.

## Replication Controller vs ReplicaSet

둘은 목적이 같지만 서로 다른 오브젝트다.

| | Replication Controller | ReplicaSet |
|---|------------------------|------------|
| 위상 | 구형 기술 | Replication Controller를 **대체하는 권장 방식** |
| apiVersion | `v1` | `apps/v1` |
| `selector` | 생략 가능 | **필수** |
| 레이블 매칭 | - | `matchLabels` 등 더 다양한 옵션 제공 |
| 생성 전부터 있던 Pod 관리 | - | 가능 (selector에 일치하면 관리 대상에 포함) |

두 가지 모두 사용할 수는 있지만 동작에 차이가 있다.

## Replication Controller

### 정의 파일

`rc-definition.yaml`

```yaml
apiVersion: v1
kind: ReplicationController
metadata:               # ReplicationController의 메타데이터
  name: myapp-rc
  labels:
    app: myapp
    type: front-end
spec:                   # ReplicationController의 사양
  template:             # 복제할 Pod의 템플릿
    metadata:           # Pod의 메타데이터
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:               # Pod의 사양
      containers:
        - name: nginx-container
          image: nginx
  replicas: 3
```

[Pods with YAML](./03.Pods%20with%20YAML.md)의 4개 최상위 필드 구조를 그대로 따른다. 달라지는 부분은 `spec`이다.

### spec 구조

`spec` 안에 **`template`** 과 **`replicas`** 두 가지를 둔다. 이 부분이 정의 파일에서 가장 중요하다.

| 필드 | 설명 |
|------|------|
| `template` | 복제본으로 만들 **Pod의 정의**. Pod 정의 파일의 `metadata`와 `spec`을 그대로 옮겨 넣는다 (`apiVersion`, `kind`는 제외). |
| `replicas` | 유지할 Pod 개수 |

- `metadata`와 `spec`이 **두 번 나온다**. 바깥쪽은 ReplicationController의 것이고, `template` 안쪽은 Pod의 것이다. 들여쓰기 레벨을 잘 구분해야 한다.
- `template`과 `replicas`는 **같은 들여쓰기 레벨**에 둔다.

### 실습

| 명령어 | 확인한 내용 |
|--------|-------------|
| `kubectl create -f rc-definition.yaml` | Replication Controller가 생성된다. |
| `kubectl get pods` | `replicas: 3` 설정대로 **Pod 3개가 자동 생성**됐다. |
| `kubectl get replicationcontroller` | `DESIRED` / `CURRENT` / `READY`가 모두 3이다. |

- Pod 이름은 `<RC 이름>-<임의 문자열>` 형식이다. 템플릿에 적은 `name: myapp-pod`가 아니라 RC 이름을 접두사로 쓴다.
- 이전 실습에서 `kubectl run`으로 따로 만든 `nginx` Pod는 RC와 관계없이 그대로 남아 있다.

| 컬럼 | 의미 |
|------|------|
| `DESIRED` | 원하는 Pod 수 (`replicas` 값) |
| `CURRENT` | 현재 존재하는 Pod 수 |
| `READY` | 준비 완료된 Pod 수 |
| `AGE` | 생성 후 경과 시간 |

`DESIRED`와 `CURRENT`가 다르면 컨트롤러가 그 차이를 맞추려고 Pod를 만들거나 지운다.

## ReplicaSet

### 정의 파일

`replicaset-definition.yaml`

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-replicaset
  labels:
    app: myapp
    type: front-end
spec:
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
        - name: nginx-container
          image: nginx
  replicas: 3
  selector:
    matchLabels:
      type: front-end
```

Replication Controller와 구조가 거의 같고, 차이는 두 가지다.

- `apiVersion`이 `apps/v1`, `kind`가 `ReplicaSet`이다.
- `spec`에 **`selector`** 가 추가된다 (**필수**).

### selector

`selector`는 ReplicaSet이 **어떤 Pod를 관리 대상으로 삼을지** 식별하는 항목이다.

```yaml
selector:
  matchLabels:
    type: front-end
```

`matchLabels` 아래에 적은 레이블이 Pod의 레이블과 일치하면 그 Pod가 관리 대상이다.

#### template에 Pod 정의가 있는데 selector가 왜 필요한가?

ReplicaSet은 **ReplicaSet을 만들 때 함께 생성되지 않은 Pod도 관리**할 수 있기 때문이다.

- 예를 들어 selector의 레이블과 일치하는 Pod가 ReplicaSet보다 먼저 만들어져 있었다면, ReplicaSet은 복제본 수를 맞출 때 **그 Pod도 개수에 포함**한다.
- 부족한 만큼만 `template`으로 새 Pod를 만든다.

#### Replication Controller와 selector

selector는 두 컨트롤러의 주요 차이점 중 하나다.

- ReplicaSet에서는 **필수 필드**다.
- `matchLabels`는 지정한 레이블을 Pod의 레이블과 단순 비교한다.
- ReplicaSet의 selector는 Replication Controller에서 쓸 수 없던 **더 다양한 레이블 매칭 옵션**을 제공한다.

### 실습

| 명령어 | 확인한 내용 |
|--------|-------------|
| `kubectl create -f replicaset-definition.yaml` | ReplicaSet이 생성된다. 결과가 `replicaset.apps/...`로 나오는 것은 `apps` API 그룹(`apps/v1`)의 오브젝트이기 때문이다. |
| `kubectl get replicaset` | 컬럼 의미는 Replication Controller와 같다. |
| `kubectl get pods` | Pod 3개가 `<ReplicaSet 이름>-<임의 문자열>` 형식으로 생성됐다. |

- 앞서 만든 `myapp-rc-*` Pod 3개도 레이블이 `type: front-end`라 selector와 겹치지만, ReplicaSet은 새 Pod를 3개 더 만들었다. 이미 다른 컨트롤러(RC)가 관리 중인 Pod는 가져오지 않기 때문이다. 이 실습은 레이블이 겹치는 상태라, 실무에서는 컨트롤러마다 레이블을 구분하는 편이 안전하다.
- RC와 ReplicaSet이 같은 클러스터에서 **동시에 동작**한다.

## ReplicaSet 동작 확인 실습

selector가 `app=myapp`이고 `replicas: 3`인 ReplicaSet으로 확인했다.

| 실습 | 명령어 | 확인한 내용 |
|------|--------|-------------|
| Pod 삭제 | `kubectl delete pod <Pod 이름>` | 삭제한 Pod 대신 **새 Pod가 자동 생성**됐다. 항상 원하는 수의 Pod가 떠 있도록 보장한다. |
| 상세 확인 | `kubectl describe replicaset <이름>` | Selector, `Replicas`(현재/원하는 수), Pod 템플릿, `Events`(생성·삭제 이력)를 볼 수 있다. 문제 추적에 쓴다. |
| 초과 Pod 생성 | `kubectl create -f nginx.yaml` | selector와 같은 레이블(`app: myapp`)의 Pod를 따로 만들자 4개가 되어, ReplicaSet이 **초과분을 바로 삭제**했다. |
| 늘리기 | `kubectl edit replicaset <이름>` | `spec.replicas`를 4로 저장하자 Pod가 하나 더 생겼다. |
| 줄이기 | `kubectl scale replicaset <이름> --replicas=2` | 4개에서 2개로 줄었다. 삭제 대상은 직접 정하지 않는다. |

### 정리

- **자동 복구:** Pod가 사라지면 ReplicaSet이 `template`으로 새로 만든다.
- **개수 유지:** `replicas`보다 적으면 만들고, 많으면 지운다. 처음부터 있던 Pod라도 레이블이 맞으면 개수에 포함된다.
- **이력 확인:** `describe`의 `Events`에 `SuccessfulCreate`, `SuccessfulDelete`로 남는다.
- **`edit`과 `scale`은 클러스터의 오브젝트만 바꾸고** 로컬 정의 파일은 바뀌지 않는다.

## 레이블과 selector가 필요한 이유

### ReplicaSet의 역할

ReplicaSet은 Pod를 **계속 모니터링**하는 프로세스다. 원하는 개수(`replicas`)보다 Pod가 줄어들면(장애 등) 새 Pod를 만들어 개수를 유지한다.

이 동작에는 두 가지가 필요하고, 정의 파일의 두 필드가 각각 맡는다.

| 필요한 것 | 담당 필드 | 설명 |
|-----------|-----------|------|
| **어떤 Pod를 감시할지** 알기 | `selector` + Pod의 `labels` | 레이블이 일치하는 Pod를 감시 대상으로 삼는다 |
| **새 Pod를 어떻게 만들지** 알기 | `template` | 부족할 때 이 정의대로 Pod를 만든다 |

### 감시할 Pod를 어떻게 아는가: 레이블

클러스터에는 Pod가 수십~수백 개 있고, 다른 애플리케이션의 Pod도 섞여 있다. ReplicaSet이 "내가 관리할 Pod"를 가려내는 기준이 **레이블**이다.

- Pod를 만들 때 레이블을 붙여 두면, ReplicaSet은 `selector`의 레이블과 비교해 대상 Pod를 찾는다.
- 컨트롤러가 Pod 목록을 따로 기억하는 것이 아니라 **레이블 조건으로 그때그때 조회**하는 방식이다.
- 그래서 **ReplicaSet보다 먼저 만들어진 Pod**도 레이블만 맞으면 대상에 들어온다. 이것이 `template`과 `selector`를 따로 두는 이유다.
- 레이블을 일찍부터 붙여 두는 것은 Pod와 애플리케이션이 많을 때 특히 유용하다 ([Pods with YAML](./03.Pods%20with%20YAML.md#레이블labels를-쓰는-이유)).

### 예시: 레이블로 대상 나누기

```
front-end Pod 3개 (type: front-end)   <- ReplicaSet A, selector: type: front-end
back-end  Pod 2개 (type: back-end)    <- ReplicaSet B, selector: type: back-end
```

ReplicaSet A는 `type: front-end`인 Pod만 세고, back-end Pod는 신경 쓰지 않는다. 레이블이 없으면 두 그룹을 구분할 방법이 없다.

### selector와 template 레이블은 일치해야 한다

`template` 안의 Pod 레이블은 `selector`와 맞아야 한다.

```yaml
spec:
  template:
    metadata:
      labels:
        type: front-end      # <- 이 레이블이
  selector:
    matchLabels:
      type: front-end        # <- selector와 일치해야 함
```

일치하지 않으면 ReplicaSet이 만든 Pod가 자기 selector에 잡히지 않아 개수를 셀 수 없으므로, 생성 단계에서 오류로 거부된다.

### 정리하면

- `selector`는 ReplicaSet이 **관리할 Pod를 고르는 조건**이다.
- `labels`는 Pod가 그 조건에 **걸리도록 붙이는 이름표**다.
- `template`은 Pod가 부족할 때 **새로 만들 Pod의 설계도**다.

## 스케일링

Pod 수를 바꾸는 방법은 세 가지다. 3개에서 6개로 늘리는 경우로 설명한다.

### 방법 1. 정의 파일 수정

`replicaset-definition.yaml`의 `replicas` 값을 바꾼 뒤 반영한다.

```yaml
spec:
  replicas: 6
```

```bash
kubectl replace -f replicaset-definition.yaml
```

`kubectl apply -f`로도 반영할 수 있다. `create`로 만든 오브젝트에 처음 `apply`하면 경고가 나올 수 있다.

### 방법 2. scale 명령어

파일을 고치지 않고 명령에서 바로 개수를 지정한다.

```bash
kubectl scale --replicas=6 -f replicaset-definition.yaml
kubectl scale --replicas=6 replicaset myapp-replicaset
```

- 첫 번째는 파일에서 대상을 찾고, 두 번째는 `타입 이름`으로 직접 지정한다.
- **정의 파일의 `replicas`는 바뀌지 않는다.** 클러스터에는 6개가 떠 있지만 파일에는 여전히 3으로 남는다. 파일을 기준으로 관리한다면 방법 1이 낫다.

### 방법 3. kubectl edit

```bash
kubectl edit replicaset myapp-replicaset
```

편집기에서 `spec.replicas`를 바꾸고 저장하면 바로 반영된다. 이것도 **로컬 정의 파일은 바뀌지 않는다.** 실습 결과는 [ReplicaSet 동작 확인 실습](#replicaset-동작-확인-실습)에 있다.

## 정리

- 컨트롤러는 오브젝트를 감시하고 상태를 맞추는 쿠버네티스의 두뇌다.
- Replication Controller / ReplicaSet은 **고가용성**(Pod 실패 시 자동 재생성)과 **부하 분산·확장**을 제공한다. Pod가 하나여도 쓸 수 있다.
- Replication Controller는 구형이고, 권장 방식은 ReplicaSet이다.
- 정의 파일은 `spec` 안에 `template`(Pod 정의)과 `replicas`(개수)를 둔다.
- ReplicaSet은 `apiVersion: apps/v1`이고 `selector`가 **필수**다. 미리 존재하던 Pod도 관리 대상에 포함할 수 있다.
- `kubectl create -f`로 만들고 `kubectl get replicationcontroller` / `kubectl get replicaset`으로 확인한다.
- ReplicaSet은 `selector`(레이블 조건)로 **감시할 Pod를 고르고**, `template`으로 **부족한 Pod를 새로 만든다**.
- 스케일링은 정의 파일의 `replicas`를 고쳐 반영하거나 `kubectl scale --replicas=N`, `kubectl edit`을 쓴다. `scale`과 `edit`은 로컬 파일을 바꾸지 않는다.
- Pod를 삭제하면 ReplicaSet이 새 Pod를 만들어 **항상 `replicas` 수를 유지**한다.
- selector에 맞는 Pod가 `replicas`보다 많아지면 초과분을 삭제한다. 사후 확인은 `kubectl describe replicaset`의 `Events`에서 한다.
