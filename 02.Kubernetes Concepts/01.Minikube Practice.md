# Minikube 실습

로컬 머신에 minikube로 단일 노드 클러스터를 만들고, 샘플 앱을 배포해 접속하는 과정을 정리한다.

## 실습 환경

| 항목 | 값 |
|------|----|
| 아키텍처 / OS | arm64 (Apple Silicon), macOS |
| 리소스 | 12코어 / 24GB RAM / 디스크 여유 500GB+ |
| 컨테이너 런타임 | Docker Desktop (minikube Docker 드라이버) |
| kubectl | v1.36.1 (Kustomize v5.8.1) |

minikube 최소 요구 사양은 2코어, 2GB 메모리, 20GB 디스크이다.

## 1. 설치 및 클러스터 생성

```bash
brew install minikube
minikube start --driver=docker   # Docker Desktop이 실행 중이어야 함
kubectl version --client         # 클라이언트 버전 확인
kubectl get nodes                # 노드가 Ready면 성공
```

- `kubectl version --client`는 클라이언트 버전만 보여 준다. 서버 버전은 클러스터가 있어야 나온다.
- kubectl과 클러스터의 버전 차이는 마이너 버전 ±1 이내여야 한다.

## 2. 샘플 앱 배포

```bash
kubectl create deployment hello-minikube --image=<이미지>
kubectl get deployments
kubectl expose deployment hello-minikube --type=NodePort --port=8080
minikube service hello-minikube --url
```

| 명령 | 설명 |
|------|------|
| `create deployment` | 이미지를 실행하는 Deployment(→ ReplicaSet → Pod) 생성 |
| `expose --type=NodePort` | 노드의 포트로 외부에서 접근 가능한 Service 생성 |
| `minikube service --url` | 서비스 접속 URL 출력 |

## 3. 접속 주소가 127.0.0.1로 나오는 이유

macOS에서 Docker 드라이버를 쓰면 minikube 노드는 Docker Desktop의 숨겨진 리눅스 VM 안에서 도는 컨테이너다.

- **Linux**: 노드 IP(예: `192.168.49.2:3xxxx`)로 직접 접속할 수 있다.
- **macOS**: 컨테이너 IP가 VM 내부 네트워크에만 있어 호스트에서 닿지 않는다.

그래서 `minikube service --url`은 `127.0.0.1`의 임의 포트에서 NodePort로 가는 **터널(포트 포워딩)** 을 연다.

```
브라우저 → 127.0.0.1:<임의 포트> → (터널) → NodePort → Service → Pod
```

- 안내 문구 "터미널을 열어야 실행할 수 있습니다"는 터널이 그 명령을 실행한 터미널 프로세스에 묶여 있다는 뜻이다.
- 해당 터미널을 닫거나 `Ctrl+C`를 누르면 접속이 끊긴다. **다른 터미널/브라우저**에서 접속한다.
- 터널을 새로 열 때마다 포트가 바뀐다.

## 4. 트러블슈팅: arm64에서 파드가 CrashLoopBackOff

### 증상

- `kubectl get deployments`의 READY가 계속 `0/1`
- `curl http://127.0.0.1:<포트>` → `Connection reset by peer`

### 진단

```bash
kubectl get pods,svc,endpoints -o wide   # 파드 상태, endpoints 확인
kubectl describe pod -l app=hello-minikube
kubectl logs deploy/hello-minikube       # 컨테이너 로그
kubectl get node -o jsonpath='{.items[0].status.nodeInfo.architecture}'
```

| 확인 결과 | 의미 |
|-----------|------|
| 파드 `Error` → `CrashLoopBackOff`, 재시작 반복 | 컨테이너가 시작 직후 종료 |
| Service의 `ENDPOINTS`가 비어 있음 | 서비스 뒤에 정상 파드가 없음 |
| 로그: `nginx: failed to initialize Lua VM` | 이미지 기동 실패 |
| 노드 아키텍처 `arm64` | 이미지와 아키텍처 불일치 의심 |

터널은 정상이지만 받아 줄 파드가 없어서 `Connection reset by peer`가 발생했다.

### 원인

`k8s.gcr.io/echoserver:1.10`이 Apple Silicon(arm64)에서 정상 기동하지 못했다. 오래된 amd64 중심 이미지라서 아키텍처가 맞지 않는 것으로 **추정**한다(이미지 매니페스트는 직접 확인하지 않음).

### 해결

arm64에서 동작하는 이미지로 교체해 Deployment와 Service를 다시 만들었다.

```bash
kubectl delete deployment,svc hello-minikube
kubectl create deployment hello-minikube --image=kicbase/echo-server:1.0
kubectl expose deployment hello-minikube --type=NodePort --port=8080
kubectl get pods -w                       # 1/1 Running 확인
minikube service hello-minikube --url     # 이 터미널은 열어 둔다
```

브라우저로 접속하면 `Request served by hello-minikube-<해시>`가 출력되어 정상 동작을 확인할 수 있다.

> 교훈: Apple Silicon에서는 이미지가 `arm64`를 지원하는지 먼저 확인한다. 파드가 `CrashLoopBackOff`면 `kubectl logs`와 노드 아키텍처부터 본다.

## 5. 정리

```bash
kubectl delete deployment,svc hello-minikube   # 리소스만 삭제
minikube stop                                   # 클러스터 중지 (데이터 유지)
minikube delete                                 # 클러스터 완전 삭제
```
