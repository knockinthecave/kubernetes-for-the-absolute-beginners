# Pods with YAML

쿠버네티스는 Pod, ReplicaSet, Deployment, Service 같은 오브젝트를 만들 때 **YAML 파일을 입력**으로 사용한다. 오브젝트 종류와 상관없이 모두 비슷한 구조를 따른다.

## 최상위 필드 4개

쿠버네티스 정의 파일에는 아래 네 가지 최상위 필드가 있고, **모두 필수**다. 하나라도 빠지면 만들 수 없다.

```yaml
apiVersion: v1
kind: Pod
metadata:
    name: myapp-pod
    labels:
        app: myapp
        type: front-end
spec:
    containers:
        - name: nginx-container
          image: nginx
```

| 필드 | 값의 형태 | 설명 |
|------|-----------|------|
| `apiVersion` | 문자열 | 오브젝트를 만드는 데 사용하는 쿠버네티스 API 버전 |
| `kind` | 문자열 | 만들려는 오브젝트의 종류 |
| `metadata` | 딕셔너리 | 이름, 레이블 같은 오브젝트 데이터 |
| `spec` | 딕셔너리 | 오브젝트의 사양 (오브젝트마다 다름) |

## apiVersion

Pod를 만들 때는 `v1`로 설정한다. 오브젝트마다 값이 다르다.

| kind | apiVersion |
|------|------------|
| Pod | `v1` |
| Service | `v1` |
| ReplicaSet | `apps/v1` |
| Deployment | `apps/v1` |

## kind

만들려는 오브젝트의 유형이다. 여기서는 `Pod`이며, 그 외에 `Service`, `ReplicaSet`, `Deployment` 등이 있다.

## metadata

오브젝트의 **이름, 레이블** 같은 부가 데이터다. 딕셔너리 형식이며 `name`과 `labels`는 그 하위 항목이다.

- `name`과 `labels`는 **같은 들여쓰기 레벨**에 둔다.
- `labels`는 딕셔너리 안의 딕셔너리 구조다.

### 레이블(labels)을 쓰는 이유

프론트엔드 Pod 수백 개와 백엔드/데이터베이스 Pod 수백 개가 배포되어 있다면, 배포 후에는 이를 그룹으로 구분하기 어렵다. 레이블을 미리 지정해두면 나중에 **필터링**하기 편하다.

- 적절하다고 생각되는 레이블을 추가해두면 오브젝트를 식별하는 데 도움이 된다.
- `labels` 아래에는 **원하는 키-값을 자유롭게** 쓸 수 있다.
- 반면 `metadata` 바로 아래에는 `name`, `labels`처럼 **쿠버네티스가 예상하는 항목만** 쓸 수 있다. 임의의 키를 추가할 수 없다.

## spec

오브젝트의 **사양** 섹션이다. 만들려는 오브젝트에 따라 내용이 달라진다.

- 오브젝트별로 어떤 필드를 쓸 수 있는지는 쿠버네티스 문서에서 제공한다. **알맞은 형식을 파악하는 것**이 가장 중요하다.
- `containers`는 **목록(배열)**이다. 하나의 Pod에 여러 컨테이너가 들어갈 수 있기 때문이다.
- `-`는 목록의 **첫 번째 항목**을 나타낸다. 컨테이너가 하나뿐인 Pod는 만들기 쉽다.

```yaml
spec:
    containers:
        - name: nginx-container   # 컨테이너 이름
          image: nginx            # 사용할 이미지
```

## Pod 생성

정의 파일을 작성한 뒤 아래 명령으로 쿠버네티스에게 Pod를 만들도록 지시한다.

```bash
kubectl create -f pod-definition.yml
kubectl get pods                      # 생성 확인
```

## 정리

- `apiVersion`, `kind`, `metadata`, `spec` 네 가지 최상위 속성을 기억한다.
- 그 다음 오브젝트에 따라 값을 추가하며 연습한다.
