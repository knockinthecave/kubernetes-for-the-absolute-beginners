# Updates and Rollback

## 롤아웃과 리비전

- Deployment를 처음 만들면 **롤아웃(Rollout)** 이 트리거된다.
- 새 롤아웃은 새 ReplicaSet을 생성하고, 애플리케이션이 업그레이드될 때마다 **새 배포 리비전(Revision)** 으로 기록된다.
- 즉, 컨테이너 버전을 새 버전으로 업데이트하면 새 롤아웃이 트리거되고 새 리비전이 만들어진다.
- 이를 통해 Deployment의 변경 사항을 추적하고, 필요하면 **이전 버전으로 롤백**할 수 있다.

| 명령어 | 설명 |
|--------|------|
| `kubectl rollout status deployment/myapp-deployment` | 롤아웃 진행 상태 확인 |
| `kubectl rollout history deployment/myapp-deployment` | 리비전과 변경 이력 확인 |

## 배포 전략

배포 전략은 두 가지가 있다. 인스턴스가 5개라고 가정한다.

| 전략 | 동작 | 특징 |
|------|------|------|
| **Recreate (다시 만들기)** | 실행 중인 5개를 **모두 삭제**한 뒤, 새 버전 인스턴스 5개를 배포 | 이전 버전이 내려가고 새 버전이 올라오기 전까지 **애플리케이션이 다운**된다. **기본 전략이 아니다.** |
| **Rolling Update (롤링 업데이트)** | 한꺼번에 내리지 않고 **하나씩** 이전 버전을 내리고 새 버전을 올림 | 중단 없이 원활하게 업그레이드된다. **기본 전략이다.** |

> Deployment를 만들 때 전략을 지정하지 않으면 **롤링 업데이트**로 동작한다.

## Deployment 업데이트 방법

업데이트는 이미 있는 정의 파일을 수정해서 적용하는 방식이 기본이다.

```bash
kubectl apply -f deployment-definition.yml
```

새 롤아웃이 트리거되고 Deployment의 새 리비전이 만들어진다.

### 트러블슈팅: `last-applied-configuration` 경고

`kubectl create -f`로 만든 Deployment에 처음 `kubectl apply`를 하면 다음 경고가 나온다.

```
Warning: resource deployments/myapp-deployment is missing the kubectl.kubernetes.io/last-applied-configuration annotation which is required by kubectl apply. ...
deployment.apps/myapp-deployment configured
```

- **원인**: `apply`는 `last-applied-configuration` 어노테이션(이전에 적용한 설정)과 새 설정을 비교해 변경분을 계산한다. `create`는 이 어노테이션을 남기지 않는다.
- **결과**: 오류가 아니다. 어노테이션이 자동으로 패치되어 `configured`로 정상 적용되고, 이후에는 경고가 나오지 않는다.
- **예방**: 처음부터 `kubectl apply -f`로 만들거나 `kubectl create -f deployment.yaml --save-config`를 사용한다.

같은 작업을 이미지만 바꾸는 명령으로도 할 수 있다.

```bash
kubectl set image deployment/myapp-deployment nginx=nginx:1.9.1
```

> **주의**: `kubectl set image`는 클러스터의 Deployment만 바꾸고 **정의 파일은 수정하지 않는다.** 이후 같은 정의 파일로 다시 `apply`하면 변경 내용이 원래대로 덮어써질 수 있으므로 주의해야 한다.

## 내부 동작: Recreate와 Rolling Update의 차이

`kubectl get replicasets`로 보면 두 전략의 차이를 알 수 있다.

1. replicas가 5개인 Deployment를 새로 만들면, 내부적으로 **ReplicaSet이 자동 생성**되고 복제본 수만큼 Pod가 만들어진다.
2. 애플리케이션을 업그레이드하면 Deployment가 내부에 **새 ReplicaSet을 생성**하고 거기에 컨테이너를 배포하기 시작한다.
3. 롤링 업데이트 전략에 따라 **이전 ReplicaSet의 Pod는 하나씩 제거**된다.
4. 결과적으로 이전 ReplicaSet(Pod 0개)과 새 ReplicaSet(Pod 5개)이 함께 보인다.

| 전략 | ReplicaSet 동작 |
|------|-----------------|
| Recreate | 이전 ReplicaSet을 0으로 줄인 뒤, 새 ReplicaSet을 5로 늘림 |
| Rolling Update | 이전 ReplicaSet을 하나씩 줄이면서 새 ReplicaSet을 하나씩 늘림 |

## 롤백

새 버전의 빌드에 문제가 있다면 Deployment의 **이전 리비전으로 되돌려** 변경 사항을 취소할 수 있다.

```bash
kubectl rollout undo deployment/myapp-deployment
```

- 새 ReplicaSet의 Pod는 **제거**되고, 이전 ReplicaSet의 Pod가 다시 **생성**되어 애플리케이션이 이전 버전으로 돌아간다.
- `kubectl get replicasets`로 보면 롤백 전의 ReplicaSet이 다시 활성화된 것을 확인할 수 있다.

## 잘못된 이미지로 업데이트하면 어떻게 될까

존재하지 않거나 받을 수 없는 이미지로 Deployment를 업데이트하는 상황을 가정한다. 이때의 동작은 롤링 업데이트가 **안전장치** 역할을 한다는 점을 보여 준다.

### 진행 과정

1. 이미지를 변경하면 업그레이드로 간주되어 **새 롤아웃**(새 리비전)이 시작된다.
2. Deployment가 새 ReplicaSet을 만들고 새 Pod를 띄우려 하면서, 이전 ReplicaSet의 Pod도 **일부만** 종료한다.
3. 새 Pod는 이미지를 받지 못해 `ErrImagePull` → **`ImagePullBackOff`** 상태가 된다. (백오프: 재시도 간격을 점점 늘리며 반복)
4. 새 Pod가 `Ready`가 되지 않으므로, Deployment는 **이전 ReplicaSet의 나머지 Pod를 더 이상 종료하지 않고** 롤아웃을 사실상 멈춘다.
5. 결과적으로 **대부분의 이전 버전 Pod는 계속 서비스**되고, 사용자 영향은 최소화된다. 롤아웃은 새 이미지가 제공되기를 기다리며 진행되지 않는다.

### 왜 이렇게 동작하나

롤링 업데이트는 새 Pod가 정상(Ready)이 된 만큼만 이전 Pod를 줄인다. 한 번에 내릴 수 있는 Pod 수와 초과로 띄울 수 있는 Pod 수에는 상한이 있다(`maxUnavailable`, `maxSurge`, 기본값 각각 25%). 새 Pod가 하나도 정상이 되지 않으면 이전 Pod를 더 내릴 수 없으므로, 잘못된 배포가 서비스 전체를 내리는 일을 막아 준다.

### 확인 방법

| 확인 대상 | 명령어 | 이상 징후 |
|-----------|--------|-----------|
| 복제본 수 | `kubectl get deployment` | `READY`, `UP-TO-DATE`가 원하는 복제본 수와 맞지 않음 |
| Pod 상태 | `kubectl get pods` | 일부 Pod가 `ImagePullBackOff` |
| 롤아웃 상태 | `kubectl rollout status deployment/myapp-deployment` | 완료되지 않고 계속 대기 |
| 이력 | `kubectl rollout history deployment/myapp-deployment` | 잘못된 이미지의 **새 리비전이 생성**되어 있음 |

### 복구

이미지 오류를 확인했다면 [롤백](#롤백)으로 이전 리비전으로 되돌린다.

```bash
kubectl rollout undo deployment/myapp-deployment
```

## 명령어 정리

| 명령어 | 설명 |
|--------|------|
| `kubectl apply -f deployment-definition.yml` | 정의 파일 변경 적용 (새 롤아웃) |
| `kubectl set image deployment/myapp-deployment nginx=nginx:1.9.1` | 이미지 직접 변경 (정의 파일은 그대로) |
| `kubectl rollout status deployment/myapp-deployment` | 롤아웃 상태 확인 |
| `kubectl rollout history deployment/myapp-deployment` | 리비전 이력 확인 |
| `kubectl rollout undo deployment/myapp-deployment` | 이전 리비전으로 롤백 |
| `kubectl get replicasets` | 이전·새 ReplicaSet 확인 |
| `kubectl get pods` | Pod 상태 모니터링 (`ImagePullBackOff` 등) |
